What is LLD?

Lecture 01 · Coder Army - System Design Full Course

Source: Coder Army — System Design Full Course, Lecture 01

01.1What LLD actually is

Low-Level Design (LLD) is the process of designing the internal structure of a software system before implementing it — classes, their data, their methods, and how they talk to each other.

Memory hook

DSA is the brain. LLD is the skeleton. DSA makes a single function fast and correct; LLD makes an entire system hold together, stay changeable, and not collapse when you add a feature six months from now.

01.2The three pillars

PillarDefinitionInterview one-liner
Scalability The ability of the system to handle growing workloads. "Will this still work at 100x the load?"
Maintainability How easily the system can be understood, modified, and debugged without breaking existing functionality. "Can a new engineer change this without fear?"
Reusability The ability to reuse existing components/modules instead of rewriting them. "Does this code act like a template?"
Design rule

Write code so it behaves like a template — a shape other parts of the system (or future features) can slot into, rather than a one-off script solving today's exact problem.

01.3Worked example — a food delivery system

Starting statement: "A user orders food from a restaurant, the restaurant prepares it, and a rider delivers it."

Fig 1.1 — the plain-English flow before any classes exist

Step 1 — identify the nouns

Underline every noun in the statement: user, order, food, restaurant, payment, rider, notification. Each noun is a potential class or object.

Step 2 — group nouns into classes

Not every noun becomes its own class — some become data or methods inside a bigger class. Grouped, the three core classes here are User, Restaurant, and Rider.

ClassData (attributes)Methods (responsibilities)
User name, address, mobileNumber placeOrder(), makePayment(), receiveNotification()
Restaurant name, orderNumber acceptOrder()
Rider deliveryTime, currentLocation pickUpOrder(), deliverOrder()
The shift that matters

This is the whole exercise: you move from identifying things (nouns) to identifying responsibilities (what each thing must be able to do). A class without a clear responsibility is a sign you grouped the nouns wrong.

01.4The general LLD workflow

Fig 1.2 — the repeatable path for any LLD problem
  1. Identify requirements — what must the system do?
  2. Identify objects — underline the nouns.
  3. Identify classes — group related objects/nouns together.
  4. Identify data in each class — the attributes.
  5. Identify methods in each class — the responsibilities.
  6. Identify relations between classes — how they interact.
  7. Ask: how can I extend this easily? — the scalability/maintainability check.
Interview trap

Jumping straight to code (or straight to class names) without the requirements → nouns → responsibilities pass is the most common way candidates lose points on LLD rounds — the interviewer is grading the process, not just the final diagram.
